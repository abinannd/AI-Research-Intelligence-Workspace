## 1. Executive Summary

The project has progressed beyond initial scaffolding, but the complete MVP has not yet been demonstrated end to end.

The repository contains substantial backend implementation for authentication, workspaces, PDF uploads, document processing, vector retrieval, AI-generated answers, and citation validation. Infrastructure configuration is also present.

However, the latest committed frontend home page inspected during this audit still displays the default Next.js starter page. The full workflow—uploading a research paper, indexing it, asking a question, receiving an evidence-grounded answer, and opening the cited PDF page—has not yet been verified as a complete working journey.

**Overall status:** Backend implementation and frontend integration stage. The MVP is not yet verified as release-ready.

> **Assessment note:** Code being present does not prove that the feature works at runtime. This report distinguishes repository implementation from independently verified behavior.

## 3. Implemented Backend Components

### 3.1 FastAPI application and API routes

The backend uses FastAPI and SQLAlchemy. The application entry point is `backend/app/main.py`.

Registered API modules include:

- `backend/app/api/auth.py`
- `backend/app/api/workspaces.py`
- `backend/app/api/documents.py`
- `backend/app/api/ask.py`

The application also exposes a `/health` endpoint.

The database models include users, workspaces, documents, chunks, queries, claims, and citations. These represent the core information required for the MVP workflow.

**Assessment:** The backend is no longer an empty scaffold. Its major functional areas have identifiable implementations.

### 3.2 Authentication and workspace isolation

The repository contains JWT authentication, password hashing, authentication dependencies, and workspace ownership checks. The security implementation is in `backend/app/security.py`.

The intended behavior is to restrict users to their own workspaces and documents.

**Remaining work:** Verify ownership enforcement for every resource-access path, including document downloads, deletion, retries, and retrieval. Add automated cross-workspace access tests.

### 3.3 PDF upload and processing

The backend implements PDF validation and processing.

Validation checks include:

- File extension and PDF signature.
- Maximum file size.
- Maximum page count.
- Whether the PDF can be opened.

The Docker Compose defaults specify a maximum file size of **20 MB** and a maximum of **80 pages**.

The parser uses PyMuPDF to extract text and identify pages that appear scanned or have insufficient extractable text. The chunking implementation creates text segments while retaining page numbers and heading metadata.

Relevant files:

- `backend/app/parsing/pdf.py`
- `backend/app/parsing/chunking.py`

**Assessment:** Basic document-processing logic is implemented. The full processing pipeline still requires runtime verification.

### 3.4 Embeddings and vector retrieval

The backend provides an embedding abstraction with two implementations:

- Deterministic hash-based embeddings.
- Sentence Transformers embeddings.

The configured embedding model is `BAAI/bge-small-en-v1.5`.

The retrieval layer supports workspace filtering and optional document filtering. Qdrant stores chunk metadata, including workspace, document, page number, heading, and text.

Relevant files:

- `backend/app/retrieval/embeddings.py`
- `backend/app/retrieval/qdrant_store.py`
- `backend/app/retrieval/retriever.py`

**Configuration consideration:** The default application settings select hash embeddings and an in-memory vector store. The Docker Compose configuration overrides these settings to select Sentence Transformers and Qdrant. The actual runtime configuration must be checked during integration testing.

### 3.5 AI question answering and citations

The question-answering pipeline:

1. Retrieves document chunks.
2. Sends retrieved evidence to the language model.
3. Processes structured claims and citation references.
4. Validates citation indices against retrieved chunks.
5. Persists the question, answer, claims, and citations.

Relevant files:

- `backend/app/citations/llm.py`
- `backend/app/citations/prompts.py`
- `backend/app/citations/qa.py`
- `backend/app/citations/validator.py`

The configured local synthesis model is `Qwen/Qwen2.5-1.5B-Instruct`. The pipeline also includes an abstention mechanism for questions that cannot be answered from retrieved evidence.

**Known limitation:** The current citation validator checks whether claims reference valid retrieved-chunk indices. This helps prevent invalid citation references, but it does not independently establish that the cited passage semantically supports the claim. Citation existence and citation correctness must be tested separately.

## 4. Frontend Status

The latest committed `frontend/src/app/page.tsx` inspected during this audit still contains the default Next.js starter interface. The global CSS and page metadata also retain default starter content.

The frontend already has a Next.js project, TypeScript configuration, API client abstraction, types, supporting libraries, and a frontend Dockerfile. Therefore, the frontend is not absent, but the committed home page does not yet implement the intended research workspace.

| Research question interface | Submit questions against ready documents | Backend endpoint exists; UI not demonstrated. |
| Answer and claims | Display answers and supporting claims | Backend response structure exists; complete UI not demonstrated. |
| Citation interaction | Select a citation to inspect its source | End-to-end behavior unverified. |

These design requirements are not reflected in the currently committed home page.

## 5. Infrastructure and Local Deployment

`infra/docker-compose.yml` defines the following services:

| Service | Purpose |
|---|---|
| PostgreSQL 16 | Persistent application data |
| Redis 7 | Background-job queue support |
| Qdrant | Vector storage and search |
| MinIO | S3-compatible PDF storage |
| FastAPI | Application API |
| Worker | Background document ingestion |
| Next.js | Web interface, enabled through the `ui` profile |

The Compose configuration includes health checks and persistent volumes for selected infrastructure services.

This is a reasonable foundation for the intended MVP, but this audit did not establish successful full-stack startup, healthy runtime services, or reproducible deployment using the current configuration.

The frontend Dockerfile uses Next.js standalone output. The frontend build and resulting container need to be tested together rather than assuming that the configuration guarantees a successful build.

**Next deployment milestone:** Start the backend-only stack, verify service health, and then start the frontend profile after its implementation and integration are ready.

## 7. Recommended Next Steps

### Priority 1 — Finish the main application interface

Replace the default Next.js landing page with the research workspace experience.

Implement authentication, workspace creation and selection, PDF upload, document-status feedback, question submission, and answer rendering. Reuse the existing API client and backend contracts instead of introducing a separate data model.

**Completion criterion:** A user can perform the supported backend operations through the interface without manually calling API endpoints.

### Priority 2 — Complete the PDF citation viewer

Implement PDF rendering, citation navigation, page selection, and quotation highlighting. Ensure the frontend consumes the backend citation metadata correctly.

**Completion criterion:** Clicking a citation opens the correct document and navigates to the cited page, highlighting the relevant passage when it can be located.

### Priority 3 — Run an end-to-end ingestion test

Start the local infrastructure and upload a valid text-based research paper.

Verify:

`Upload → Queue → Parse → Chunk → Embed → Index → Ready`

Then test a scanned or text-poor document and an invalid file.

**Completion criterion:** Document states are accurate, indexing failures are visible, and retry/delete operations behave consistently.

### Priority 4 — Validate grounded question answering

Use research papers with questions whose answers can be checked against specific pages.

Test:

- Answers supported by uploaded documents.
- Questions with no supporting evidence.
- Invalid or unavailable citation indices.
- Queries restricted to selected documents.
- Attempts to retrieve information from another workspace.

**Completion criterion:** Citations reference retrieved evidence, unsupported claims are handled correctly, and workspace boundaries are enforced.

### Priority 5 — Establish automated verification

Run the backend test suite, frontend linting and production build, and integration checks.

Prioritize tenant isolation, document lifecycle transitions, citation validation, and the complete upload-to-answer-to-page-navigation workflow.

Document a reproducible setup process and ensure secrets are not committed.

**Completion criterion:** A fresh checkout can be configured, started, and verified using documented commands.

| 6 | Graceful handling of storage, worker, and network failures | 🟡 Systematic integration testing needed |

### MVP completion definition

Do not consider the MVP complete merely because its major files exist or the frontend compiles.

The release milestone is a successful demonstration of this entire journey:

**Create workspace → Upload PDF → Wait for indexing → Ask a research question → Receive an evidence-grounded answer → Click a citation → Inspect the cited page.**

This is the product slice identified in `init_plan.md`. Comparison, evidence graphs, large-scale Celery infrastructure, OCR, and advanced evaluation should remain deferred until this journey works reliably.

## 9. Recommended VS Code + Copilot Workflow

Continue with the existing repository and implement the MVP in small, verifiable increments.

1. Finish the main workspace UI and integrate it with existing APIs.
2. Complete the PDF citation viewer.
3. Run the full ingestion pipeline and fix integration failures.
4. Validate citation grounding, workspace isolation, and error handling.
5. Complete the documented acceptance tests and local deployment instructions.

Keep each task bounded. Have Copilot inspect the relevant files and contracts before editing, then run the corresponding checks before moving to the next task. This reduces regressions and avoids unnecessary rewrites of working backend components.

## 10. Final Verdict

The project is in the **backend implementation and frontend integration stage**, not at the beginning of development and not yet at a verified MVP release.

The major architecture and backend building blocks are present. The highest-priority gap is completing the frontend workflow, especially the PDF citation viewer, and then proving that the entire system works together.

**Immediate next milestone:** Deliver and verify the complete upload-to-cited-answer-to-page-viewer journey.
